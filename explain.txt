The current code is intentionally kept in one Home.jsx file, with nested/component

Home

 |           +-- ProductCard
 |

 |

 |

 |

Important ownership rule:

Home owns the cart.

Why?

Because many ProductCards need to affect the same cart, and the Cart popup also needs
to read the same cart.

The shape is:

                      Home
                       |
                    cart state
                       |
          +------------+-------------+
          |            |             |
     ProductCard   ProductCard   Cart Popup

This is the React idea called LIFTING STATE UP.

If two components need the same data, keep the shared state in their common parent.

Concepts:

The first is a named export imported by name. The second imports the module's default

06. API FETCHING
======================================================================

The menu-loading effect is:

useEffect(() => {
  async function getMenu() {
    try {
      const data = await api.GetMenuItems();

      console.log("MENU RESPONSE:", data);

      if (data.success === 1) {
        setMenu(data.data);
      }
    } catch (error) {
      console.error("MENU ERROR:", error);
    }
  }

  getMenu();
}, []);

Concepts:
- useEffect
- async/await
- Promise
- try/catch
- conditional logic
- state update
- dependency array

What does the empty [] mean?

It means the effect is intended to run after the initial mount rather than after every
render.

Conceptual sequence:

component mounts
    ->
useEffect runs
    ->
getMenu()
    ->
api.GetMenuItems()
    ->
Promise resolves
    ->
data returned
    ->
setMenu(data.data)
    ->
React re-renders

Why do we not put the API call directly in the render body?

Because rendering should not repeatedly trigger side effects such as network calls.

INTERVIEW Q:
Why use useEffect for an API call in this client component?

ANSWER:
Because fetching data is a side effect. useEffect lets the component run that side
effect as part of the component lifecycle rather than during render.

07. LOCALSTORAGE AND HYDRATION
======================================================================

The cart is persisted in localStorage using:

const CART_STORAGE_KEY = "atf_cart";

Initial React state:

const [cart, setCart] = useState([]);

Then:

useEffect(() => {
  try {
    const savedCart = localStorage.getItem(CART_STORAGE_KEY);

    if (savedCart) {
      const parsedCart = JSON.parse(savedCart);

      if (Array.isArray(parsedCart)) {
        setCart(parsedCart);
      }
    }
  } catch (error) {
    console.error("CART LOAD ERROR:", error);
  } finally {
    setCartHydrated(true);
  }
}, []);

Saving:

useEffect(() => {
  if (!cartHydrated) return;

  try {
    localStorage.setItem(
      CART_STORAGE_KEY,
      JSON.stringify(cart)
    );
  } catch (error) {
    console.error("CART SAVE ERROR:", error);
  }
}, [cart, cartHydrated]);

Very important concepts:

localStorage stores strings.

So:
JavaScript array/object
    ->
JSON.stringify()
    ->
string
    ->
localStorage

And when reading:
string
    ->
JSON.parse()
    ->
JavaScript array/object

WHY CARTHYDRATED?

Because Next.js can render on the server.

The browser has localStorage.
The server does not.

If initial state reads localStorage during the first render, you can get:

SERVER:
cart = []

CLIENT:
cart = saved cart

Then server HTML and client HTML can differ.

That is a hydration mismatch.

The safer pattern is:

initial render
cart = []

then after mount:
load localStorage
setCart(saved cart)

Only after loading do we allow saving.

That is what this guard does:

if (!cartHydrated) return;

It prevents the initial empty array from immediately overwriting the existing saved cart.>
INTERVIEW Q:

Why is localStorage accessed inside useEffect?

ANSWER:
Because localStorage is a browser API and the component may be rendered in an environment
where browser globals are unavailable during server rendering.

11. createCartItemId()
======================================================================

The function:

const createCartItemId = ({
  product,
  preference,
  variation,
  addons
}) => {
  const addonIds = addons
    .map((addon) => addon.addon_id)
    .sort()
    .join("-");

  return [
    product.product_id,
    preference || "",
    variation?.variation_id || "",
    addonIds,
  ].join("|");
};

This is one of the most important functions in the project.

WHY?

Because the same base product can exist in many configurations.

Example:

Nachos + Regular
Nachos + Jain
Nachos + Regular + Cheese
Nachos + Regular + Cheese + Salsa

These must not accidentally merge.

The ID therefore combines multiple identity components:

product ID
+
preference
+
variation ID
+
addon IDs

Example:

10|Jain|2|5-8

That can be read as:

product = 10
preference = Jain
variation = 2
extras = 5,8

CONCEPTS USED:
- destructuring
- map()
- sort()
- join()
- optional chaining
- logical OR fallback
- array
- string construction

WHY sort()?

Suppose selected extras are:

[5, 8]

Another time they are selected in reverse order:

[8, 5]

Without sorting, IDs would become:

5-8
and
8-5

Those are actually the same set of extras but would look different.

sort() normalizes the order.

IMPORTANT:
This is an example of canonicalization: different input order can be converted to one
consistent representation.

12. addToCart()
======================================================================

The function:

const addToCart = ({
  product,
  preference,
  variation,
  addons,
  price
}) => {

  const cartItemId = createCartItemId({
    product,
    preference,
    variation,
    addons,
  });

  const minimumQuantity =
    Number(product.minimum_quantity) || 1;

  setCart((currentCart) => {
    const existingItem = currentCart.find(
      (item) => item.cartItemId === cartItemId,
    );

    if (existingItem) {
      return currentCart.map((item) =>
        item.cartItemId === cartItemId
          ? {
              ...item,
              quantity:
                item.quantity + minimumQuantity,
            }
          : item,
      );
    }

    return [
      ...currentCart,
      {
        cartItemId,
        product,
        preference,
        variation,
        addons,
        price,
        quantity: minimumQuantity,
      },
    ];
  });
};

There are TWO paths.

PATH A:
Exact configuration already exists.

Then increase its quantity.

PATH B:
Exact configuration does not exist.

Then append a new cart item.

This is classic "search then update/insert" logic.

----------------------------------------------------------------------
12A. Why Number()?
----------------------------------------------------------------------

API values can sometimes arrive as strings.

Number("2") -> 2

So:

Number(product.minimum_quantity)

converts the value to a number.

Then:

|| 1

provides a fallback.

If the converted value is invalid/falsy for the intended use, use 1.

----------------------------------------------------------------------
12B. Why functional setState?
----------------------------------------------------------------------

setCart((currentCart) => { ... })

This is preferred when the next state depends on the previous state.

Pattern:

setState(previous => next)

This makes the relationship explicit.

----------------------------------------------------------------------
12C. Why find() first?
----------------------------------------------------------------------

find() answers:

"Does the exact cart item already exist?"

Example:

const item = array.find(
  (x) => x.id === targetId
);

If found:
returns object.

If not:
returns undefined.

----------------------------------------------------------------------
12D. Why map() after find()?
----------------------------------------------------------------------

When an item exists, we need a new cart array where ONLY the matching item has a new
quantity.

That is what map() does.

----------------------------------------------------------------------
12E. Why spread operator?
----------------------------------------------------------------------

{
  ...item,
  quantity: item.quantity + minimumQuantity
}

This copies existing item properties and replaces quantity.

If item is:

{
  name: "Nachos",
  price: 200,
  quantity: 1
}

then:

{
  ...item,
  quantity: 2
}

becomes:

{
  name: "Nachos",
  price: 200,
  quantity: 2
}

This is immutable-style updating.

----------------------------------------------------------------------
12F. Why not currentCart.push(...)?
----------------------------------------------------------------------

Because push mutates the original array.

In React state, it is much safer and clearer to create a new array:

[
  ...currentCart,
  newItem
]

This preserves immutability.

13. find(), map(), filter(), reduce()
======================================================================

These four methods are central to the project.

find()
------
Search for one item.

Example:
const item = cart.find(
  (item) => item.cartItemId === id
);

Returns:
one object or undefined.

map()
-----
Transform every item.

Example:
cart.map(item => ...)

Returns:
new array of same logical length.

filter()
--------
Keep items that satisfy a condition.

Example:
cart.filter(
  item => item.cartItemId !== id
);

Returns:
new array, often with fewer items.

reduce()
--------
Combine many items into one result.

Example:
cart.reduce(
  (total, item) => total + item.quantity,
  0
);

Returns:
one final value.

MEMORY TRICK:

find = find ONE
map = make/transform MANY
filter = keep/remove MANY
reduce = reduce MANY to ONE

14. SPREAD OPERATOR AND IMMUTABILITY
======================================================================

Array spread:

[
  ...currentCart,
  newItem
]

Object spread:

{
  ...item,
  quantity: newQuantity
}

The spread operator copies values into a new structure.

Why do this?

Because React state should be updated through new references instead of mutating the
existing state object/array in place.

BAD style:

cart.push(newItem);

BETTER:

setCart([
  ...cart,
  newItem
]);

BAD style:

item.quantity = item.quantity + 1;

BETTER:

{
  ...item,
  quantity: item.quantity + 1
}

This concept becomes extremely important with React.

16. AVAILABILITY LOGIC
======================================================================

The product has an availability object with weekday keys.

The function:

const checkAvailability = () => {
  const availability = product.availability;

  if (!availability) {
    return false;
  }

  const days = [
    "sunday",
    "monday",
    "tuesday",
    "wednesday",
    "thursday",
    "friday",
    "saturday",
  ];

  const today = days[new Date().getDay()];

  return availability[today] === 1;
};

Step by step:

1. Get availability object.
2. If missing, return false.
3. Get current day number using new Date().getDay().
4. Convert day number to the API's weekday key.
5. Read availability[today].
6. Only value 1 means available.

Example:
getDay() returns 1
days[1] = "monday"

Then:
availability["monday"] === 1

This is dynamic property access.

IMPORTANT:
getDay() returns a number from 0 to 6 with Sunday at 0.

The array order is therefore deliberate.

17. DYNAMIC PRODUCT PRICING

const variationPrice = selectedVariation

const finalPrice =

18. ADD-ONS / EXTRAS
======================================================================

The API's multiple_addons are rendered as checkboxes.

The code checks whether an addon is selected:

const checked = selectedAddons.some(
  (item) => item.addon_id === addon.addon_id
);

some() returns true/false.

Then toggleAddon():

const toggleAddon = (addon) => {
  setSelectedAddons((current) => {
    const exists = current.some(
      (item) => item.addon_id === addon.addon_id
    );

    if (exists) {
      return current.filter(
        (item) => item.addon_id !== addon.addon_id
      );
    }

    return [...current, addon];
  });
};

This is a toggle pattern.

If exists:
remove.

If not exists:
add.

Conceptually:

checkbox click
  ->
is selected?
  -> YES -> filter it out
  -> NO  -> spread + append it

IMPORTANT:
Checkboxes allow MULTIPLE extras.

That is why selectedAddons is an array.

19. QUANTITY LOGIC
======================================================================

increaseQuantity():

const increaseQuantity = () => {
  if (!cartItem) return;

  updateCartQuantity(
    cartItem.cartItemId,
    cartItem.quantity + 1
  );
};

decreaseQuantity():

const decreaseQuantity = () => {
  if (!cartItem) return;

  if (cartItem.quantity <= 1) {
    return;
  }

  updateCartQuantity(
    cartItem.cartItemId,
    cartItem.quantity - 1
  );
};

This includes guard clauses.

Guard clause:

if (!cartItem) return;

Meaning:
If there is nothing to update, stop immediately.

The second guard:

if (cartItem.quantity <= 1) return;

enforces the business rule:
Quantity cannot go below 1.

Notice:
"Minus at 1" does NOT remove the item.

Deletion is a separate action:
Clear.

This is a UI/business-rule decision.

const handlePlaceOrder = () => {
  setOrderError("");

25. handleOrderChange()
======================================================================

The function:

const handleOrderChange = (event) => {
  const { name, value } = event.target;

  setOrderForm((current) => ({
    ...current,
    [name]: value,
  }));

  if (orderError) {
    setOrderError("");
  }
};

This is a very reusable form pattern.

FIRST:
const { name, value } = event.target;

This destructures:
event.target.name
event.target.value

SECOND:
setOrderForm(...)

THIRD:
...current

preserves all old fields.

FOURTH:
[name]: value

updates the specific field dynamically.

Example:

name = "mobile"
value = "9999999999"

then:

[name]: value

becomes:

mobile: "9999999999"

This lets ONE handler manage many inputs.

This is one of the most useful React form techniques to memorize.

26. FORM VALIDATION
======================================================================

The pickup fields are represented as:

const requiredPickupFields = [
  ["name", "Please enter your name."],
  ["mobile", "Please enter your mobile number."],

Delivery fields include:

const requiredDeliveryFields = [
  ["name", "..."],
  ["mobile", "..."],
  ["houseFlat", "..."],
  ["buildingName", "..."],
  ["tower", "..."],
  ["floor", "..."],

  ["landmark", "..."],

];

Then:

  orderType === "pickup"
    ? requiredPickupFields
    : requiredDeliveryFields;

This is an example of DRY thinking:
Don't write two completely separate validation functions when the structure can be

This combines:
- find()
- destructuring
- dynamic object property access
- trim()
- negation

If a field is blank:

Then:

if (missingField) {
  setOrderError(missingField[1]);
  return;
}

The function exits.

That is a guard/early-return pattern.

27. trim(), replace(), AND REGEX
======================================================================

TRIM
----

"   Yuvraj   ".trim()

becomes:

"Yuvraj"

Used to prevent input containing only spaces from passing validation.

REPLACE WITH REGEX
------------------

const cleanMobile =
  orderForm.mobile.replace(/\D/g, "");

Here:
\D means "not a digit".

g means global, so all matching characters are replaced.

Example:
"98765-43210"
may become:
"9876543210"

This is useful when you want to validate digit count even if the user typed separators.

MOBILE CHECK
------------

if (cleanMobile.length < 10) {
  ...
}

This is a minimum-length check.

PINCODE REGEX
-------------

if (
  orderType === "delivery" &&
  !/^\d{6}$/.test(orderForm.pincode.trim())
)

Pattern:
^      start
\d     a digit
{6}    exactly six times
$      end

So it expects exactly six digits.

31. filter() FOR MESSAGE CLEANUP
======================================================================

32. encodeURIComponent()
======================================================================

The message is placed inside a URL:

const whatsappUrl =
  `https://wa.me/${WHATSAPP_NUMBER}?text=${
    encodeURIComponent(message)
  }`;

Why encode?

Because URLs have special syntax.

A message can contain:
- spaces
- ampersands
- question marks
- new lines
- currency symbols
- punctuation

encodeURIComponent converts the message to URL-safe text.

Without encoding, some characters could be interpreted as part of URL syntax instead of
message content.

This is a browser/web-platform concept rather than a React-specific one.

36. PARENT / CHILD COMMUNICATION AND PROPS
======================================================================

Home renders Category with:

  cart={cart}
  addToCart={addToCart}
  updateCartQuantity={updateCartQuantity}
  removeFromCart={removeFromCart}

Then Category passes these into ProductCard.

A function passed as a prop is often called a callback prop.

Parent:
<Category addToCart={addToCart} />

Child:
<ProductCard addToCart={addToCart} />

Grandchild:
addToCart(...)

The child does not own the cart.
It asks the parent-owned cart state to change.

This is a major React architecture pattern.

37. LIFTING STATE UP
======================================================================

Why is cart in Home rather than inside ProductCard?

Because multiple ProductCards need to share one cart.

If every ProductCard had its own:

const [cart, setCart] = useState([])

then:
Product 1 would have cart A.
Product 2 would have cart B.
Cart popup would have another cart.

That would be wrong.

Instead:

Home owns one cart.

ProductCards receive:
cart
addToCart
updateCartQuantity
removeFromCart

This is state lifting.

Rule to remember:

IF MULTIPLE COMPONENTS NEED THE SAME STATE,
KEEP THAT STATE IN THEIR CLOSEST COMMON PARENT.

38. CONDITIONAL RENDERING
======================================================================

There are three common patterns in the project.

1. &&

  <CartButton />

Meaning:
render only when condition is truthy.

2. TERNARY

orderType === "pickup"
  ? pickupFields
  : deliveryFields

Meaning:

3. EARLY RETURN IN JS

if (!cartItem) return;

This is not JSX conditional rendering, but it controls code execution.

Conditional rendering is one of the most important React skills to master.

======================================================================
39. OPTIONAL CHAINING AND FALLBACKS
======================================================================

Examples:

selectedVariation?.variation_id

Meaning:
If selectedVariation exists, access variation_id.
Otherwise return undefined instead of throwing.

Other example:

product.product_variations || []

Meaning:
if product.product_variations is missing/falsy, use an empty array.

This is useful for API data that may omit optional fields.

Other example:

product.price || 0

Meaning:
use product.price when it is truthy; otherwise use 0.

IMPORTANT:
Optional chaining and fallback operators solve different problems.

?. protects property access.

|| provides an alternative value.

40. DERIVED VALUES
======================================================================

Examples:

variationPrice
addonsPrice
finalPrice
quantity
cartCount
itemTotal
total

These can be calculated from existing state/data.

Example:

const cartCount = cart.reduce(
  (total, item) => total + item.quantity,
  0
);

We do not need separate state for cartCount.

This avoids duplicated state.

Duplicated state creates synchronization bugs.

Rule:
If value can be calculated directly from existing state/props, prefer deriving it.

45. INTERVIEW / VIVA QUESTIONS AND ANSWERS
======================================================================

Q1. Why is the cart state in Home?
A:
Because many ProductCards and the Cart popup need the same cart. Home is their common
parent, so the state is lifted there.

Q2. Why use setCart(currentCart => ...)?
A:
Because the new cart depends on the previous cart.

Q3. Why use find() before map()?
A:
find() checks whether the exact cart configuration already exists. map() can then update
the matching item immutably.

Q4. Why use filter() to remove a cart item?
A:
filter() returns a new array without the matching item.

Q5. Why not use push()?
A:
push() mutates the existing array. React state updates are clearer and safer when a new
array is produced.

Q6. Why is cartItemId more than product_id?
A:
The same base product can have different preferences, variations, and extras. Those
configurations should be distinct cart items.

Q7. Why sort addon IDs?
A:
To make the ID consistent even if the user selects the same extras in a different order.

Q8. Why use reduce() for cart count?
A:
Because we need one total number from many cart items.

Q9. Why is finalPrice not state?
A:
It is derivable from product price, variation price, and addon price.

Q10. What is a controlled input?
A:
An input whose value is controlled by React state.

Q11. Why one handleOrderChange for many inputs?
A:
Because event.target.name identifies the field and [name]: value dynamically updates the
correct object property.

Q12. What does [name]: value mean?
A:
It is a computed property name. The object key is determined by the value of name.

Q13. Why use trim()?
A:
To reject input that contains only whitespace and to normalize validation.

Q14. What does /\D/g do?
A:
It targets every non-digit character.

Q15. What does /^\d{6}$/ validate?
A:
Exactly six digits from beginning to end.

Q16. Why use encodeURIComponent()?
A:
To encode the message so it can safely be placed inside a URL query parameter.

Q17. Does Order on WhatsApp call a backend API?
A:
No. In the current code it builds a WhatsApp URL and uses window.open().

Q18. Why use useEffect for localStorage?
A:
Because localStorage is a browser API and should not be relied on during server rendering.

Q19. What caused the earlier hydration issue?
A:
If the initial client render reads saved localStorage data while the server starts with an
empty cart, the generated HTML can differ.

Q20. Why does cartHydrated exist?
A:
To delay saving until the initial localStorage load has finished.

Q21. What does JSON.stringify do?
A:
Converts a JavaScript object/array into a JSON string.

Q22. What does JSON.parse do?
A:
Converts a JSON string back into a JavaScript value.

Q23. What is a callback prop?
A:
A function passed to a child so the child can trigger logic owned by the parent.

Q24. What is a guard clause?
A:
A condition that immediately exits a function when a required condition is not met.

Q25. Why use optional chaining?
A:
To safely access a nested property when an object may be null/undefined.

Q26. What is conditional rendering?
A:
Rendering different JSX depending on a condition/state value.

Q27. What is derived data?
A:
A value that can be calculated from existing state/props rather than stored separately.

Q28. Why are notes optional?
A:
The validation list intentionally excludes notes, while the message conditionally adds
them only when non-empty.

Q29. What happens if availability is missing?
A:
checkAvailability() returns false, so the item is treated as unavailable by this logic.

Q30. What happens when quantity is 1 and the user presses minus?
A:
Nothing. The function returns, preserving the business rule that quantity cannot fall below 1.

Q31. What removes an item?
A:
removeFromCart(), which uses filter().

Q32. What empties the entire cart?
A:
clearAllCart(), which sets cart to [] and closes the cart popup.

47. COMMON MISTAKES
======================================================================

Mistake 1:
Mutating React state directly.

Bad:
cart.push(item)

Better:
setCart([...cart, item])

Mistake 2:
Using product_id only as cart identity.

Problem:
Different configurations merge.

Better:
Use composite identity.

Mistake 3:
Storing finalPrice in state unnecessarily.

Problem:
Extra synchronization.

Better:
Calculate it.

Mistake 4:
Reading localStorage during initial render in a Next.js page that must hydrate
consistently.

Problem:
Hydration mismatch.

Better:
Load after mount.

Mistake 5:
Saving localStorage immediately before load finishes.

Problem:
Existing cart can be overwritten with [].

Better:
wait for cartHydrated.

Mistake 6:
Using one giant change handler without using input names.

Problem:
Harder to scale.

Better:
name/value + computed property key.

Mistake 7:
Treating the WhatsApp action as a real backend order API.

Problem:
Wrong mental model.

Current implementation is URL-based handoff to WhatsApp.
